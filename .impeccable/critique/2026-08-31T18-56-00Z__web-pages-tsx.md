# Submit page critique against Zet's review

## Verdict

The page now separates the connected signer from deployment identity, but it still implements a fixed listing form with an optional modular appendix. Zet asked for the opposite hierarchy: resolve the enforcer identity, then construct a repeatable list of claims.

## Strengths

- The deployed contract, optional deployer claim, and connected signing wallet are no longer conflated.
- The identity is correctly expressed as a chain-qualified CAIP/EIP-155 deployment.
- The wallet-owned review and simulation sequence is careful and transparent.

## Priority issues

### P1 — Fixed claims still define the workflow

The UI says “These five core claims make the record usable” and requires purpose, source, restriction, operation, and terms before submission. This is the exact rigidity Zet described. Flexible claims appear later as “extra evidence,” so the implementation preserves the old model with an extension rather than adopting his identity-plus-claims model.

### P1 — The claim composer cannot create or discover arbitrary predicates

Known predicates are selectable, but a custom predicate requires an exact Intuition atom ID. A contributor cannot search for a predicate by readable label, select an existing term, or create a new predicate atom within the flow. This does not meet “select the predicate and create the object, then repeat.”

### P1 — The page exposes the entire transaction schema at once

Identity, five fixed claims, a large JSON schema editor, optional evidence claims, wallet connection, and a submission outline coexist in one long page. The user does not complete and collapse Step 1 before entering Step 2, so the visual hierarchy does not behave like a guided two-step contribution.

### P2 — Templates are secondary rather than the primary claim entry point

Audit, usage, composability, deployer, and author templates are small shortcut buttons below the fixed ledger. They should be the starter menu for repeatable claim rows, with a general “Other claim” path alongside them.

### P2 — Technical IDs impose avoidable recall burden

Custom predicate and existing-term claims ask for 32-byte IDs without a registry-backed picker. Advanced IDs should remain available, but behind readable search/select/create controls.

## Recommended construction

1. **Identity** — chain plus contract address; lookup existing identity or prepare a new atom. Display name is optional metadata.
2. **Claims** — begin with an empty repeatable list. Each claim has subject, predicate, and object. Starter cards add Source, Purpose, Terms, Restriction, Chain, Author, Deployer, Audit, Usage, and Composability rows, but none permanently closes the ontology.
3. **Review and write** — show the exact atoms/triples, required TRUST, connected signer, simulation, and approval only after the contributor advances from claims.

Only the minimum graph structure needed for registry membership should be created automatically. Everything semantic should appear as an explicit claim the contributor can inspect, remove, or add.

## Persona impact

- **Protocol contributor:** blocked by mandatory claims that may not describe the contribution they intend to make.
- **Reviewer/curator:** benefits from explicit claims, but the current form obscures which claims were chosen by the contributor versus imposed by the app.
- **Developer with an existing deployment:** can identify the contract correctly, but must understand raw Intuition IDs to express an unanticipated relationship.
- **Returning power user:** JSON import is efficient, but the normal interface remains slower than a true claim-list builder.
